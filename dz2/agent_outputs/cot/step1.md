# Шаг 1. Рассуждение и спецификация фильтра дашборда

Чистая функция дашборда читает уже переданный список, фильтр и момент `now`. Она ничего не запрашивает из сети и базы, не читает системные часы и не меняет входной массив. Подписи интерфейса («К выполнению», «В работе», «Готово») остаются снаружи: модуль возвращает данные, а не текст экрана.

Идентификатор `id` в этом контракте — непрозрачная строка. Приоритет хранится в задании и проходит в результат как есть: на отбор, сводку и порядок он не влияет. Значение фильтра «все статусы» в типе называется `all` (в интерфейсе это подпись «все»). Пустая строка означает «все предметы» только у поля `course`.

Момент сравнивается как абсолютное время: строка разбирается через `Date.parse`, а не как текст. `dueAt < now` — строгое сравнение разобранных меток. Равенство меток просрочкой не является. Строка, которую `Date.parse` не превращает в конечное число, считается невалидной датой.

Если невалиден сам `now`, функция не бросает исключение: ни одно задание не помечается просроченным, а порядок строится по валидным `dueAt` и названию. Вызов с корректным `now` остаётся основным контрактом.

## 1. Логические шаги

### Шаг 1. Разобрать дату и отметить просрочку на исходном списке

Для каждого задания проверяю две вещи. Первая: `dueAt` разбирается в конечную метку времени. Вторая: метка строго меньше `now`, а `status` при этом `todo` или `in_progress`. Оба условия вместе дают признак «просрочено». Невалидная дата этот признак не получает.

Этот шаг стоит первым, потому что на одном и том же признаке держатся включение `onlyOverdue`, счётчик `overdue` и группа «сначала просроченные». Если определить признак после фильтра или отдельно для сводки и для списка, цифры и порядок разъедутся. Здесь же снимается риск падения: битая дата получает класс «валидной метки нет» до любого сравнения и до сортировки.

### Шаг 2. Посчитать сводку по полному списку

По исходному списку, уже размеченному на шаге 1, считаю:

- `total` — число заданий;
- `todo`, `inProgress`, `done` — числа по полю `status`;
- `overdue` — число заданий с признаком просрочки.

Просроченное задание со статусом `todo` увеличивает и `todo`, и `overdue`. Просроченное `in_progress` увеличивает и `inProgress`, и `overdue`. Статус `done` увеличивает только `done` и `total`, даже если календарная дата уже в прошлом. Невалидная дата участвует в счётчике своего статуса и в `total`, а в `overdue` не входит. Отсюда инвариант: `total = todo + inProgress + done`, и `overdue` не больше `todo + inProgress`.

Сводка считается до отбора. Фильтр на неё не влияет. Если посчитать её по уже отфильтрованному списку, дашборд покажет объём видимой выборки вместо объёма всех заданий студента.

### Шаг 3. Отобрать задания конъюнкцией трёх условий

В видимый список попадает задание, которое проходит все три проверки сразу.

1. Статус. При `filter.status = "all"` статус не ограничивает выборку. Иначе поле `status` совпадает с фильтром. Просрочка сама по себе задание не исключает: при `onlyOverdue = false` просроченное задание остаётся, если его статус и предмет подходят.
2. Предмет. Строка фильтра обрезается по краям. Пустой результат означает «все предметы». Иначе сравниваются предмет задания и строка фильтра после обрезки краёв и приведения к нижнему регистру локалью `ru`. Пробелы внутри строки значимы.
3. Просрочка. При `onlyOverdue = true` остаётся только задание с признаком из шага 1. При `false` эта проверка ничего не отсекает.

Отбор идёт после сводки, потому что сводке нужен полный список, а сортировке — уже видимый. Сортировать исходный список раньше отбора бессмысленно: в ответ должны попасть только прошедшие три проверки, а цифры сводки от порядка не зависят.

### Шаг 4. Упорядочить видимый список

Сортируется только массив шага 3. Ключи такие:

1. Сначала задания с признаком просрочки. У всех них дата валидна: иначе признак на шаге 1 не ставится.
2. Затем валидный `dueAt` по возрастанию метки времени.
3. При равной метке — `title` через сравнение локалью `ru`.
4. Невалидный `dueAt` стоит после всех валидных дат. Между собой такие задания тоже сравниваются по `title` локалью `ru`.
5. При равном названии сохраняется исходный порядок списка (сортировка устойчивая).

Этот шаг последний: множество элементов появляется только после отбора, а группа просрочки и «конец списка» для битой даты определены ещё на шаге 1. Сравнение идёт по меткам времени, поэтому смещение часового пояса в ISO-строке не ломает порядок и не роняет выполнение.

Наружу уходит новый массив и сводка шага 2. Объекты заданий и входной массив не изменяются.

## 2. Типы

```typescript
type AssignmentStatus = "todo" | "in_progress" | "done";

type AssignmentPriority = "low" | "medium" | "high";

type Assignment = {
  id: string;
  title: string;
  course: string;
  dueAt: string;
  status: AssignmentStatus;
  priority: AssignmentPriority;
};

type AssignmentFilter = {
  status: AssignmentStatus | "all";
  course: string;
  onlyOverdue: boolean;
};

type AssignmentSummary = {
  total: number;
  todo: number;
  inProgress: number;
  done: number;
  overdue: number;
};

type DashboardData = {
  items: Assignment[];
  summary: AssignmentSummary;
};
```

`AssignmentStatus` и `AssignmentPriority` задают поля `Assignment` и статус фильтра. В `DashboardData.items` лежит отфильтрованный и отсортированный список. В `summary` лежат счётчики исходного списка.

## 3. Краевые случаи

| Случай | Что подаём | Что ожидаем |
| --- | --- | --- |
| Пустой список | `assignments = []`, любой допустимый фильтр, валидный `now` | `items` пуст. `total`, `todo`, `inProgress`, `done`, `overdue` равны 0. Исключения нет. |
| Все готово, дата в прошлом | У каждого задания `status = "done"`, валидный `dueAt` строго раньше `now` | Признак просрочки ни у кого не стоит. `overdue = 0`, `done = total`. При `onlyOverdue = false` и статусе `all` в списке все задания, по возрастанию `dueAt`, при равенстве — по `title` локалью `ru`. При `onlyOverdue = true` видимый список пуст, сводка исходного списка сохраняется. |
| Битая дата | `dueAt`, который `Date.parse` не превращает в конечное число; рядом есть задания с валидными датами | Исключения нет. Битая дата не увеличивает `overdue` и учитывается в счётчике своего статуса. В видимом списке, если задание прошло фильтр, оно стоит после всех валидных дат. Два таких задания упорядочиваются по `title` локалью `ru`. |
| Пробелы в названии предмета | У задания `course = "  Алгебра "`, фильтр `course = "алгебра"`. Отдельно фильтр из одних пробелов `"   "` | Первая пара совпадает: края обрезаются, регистр `ru` не мешает. Внутренние пробелы по-прежнему различают строки. Фильтр из одних пробелов после обрезки пуст и означает «все предметы». |
| `onlyOverdue` вместе со статусом `done` | `onlyOverdue = true`, `filter.status = "done"`, в исходном списке есть и готовые задания с прошлой датой, и просроченные `todo` | Видимый список пуст: готовое задание просроченным не бывает, а просроченный `todo` не проходит фильтр статуса `done`. Сводка считается по исходному списку: `done` и `overdue` отражают полный набор, а не пустую выборку. |

## 4. Промпты следующих шагов

### Промпт шага 2

**Role:** Ты senior-разработчик приложения «Дедлайн». Пишешь типобезопасный TypeScript. Доменные функции не смешиваешь с React, HTTP, SQL и системными часами.

**Task:** Реализуй чистые функции фильтрации и сводки учебных заданий по спецификации шага 1. Код интерфейса не пиши и компоненты не меняй.

Контракт функций:

- `isAssignmentOverdue(assignment: Assignment, now: string): boolean`
- `summarizeAssignments(assignments: readonly Assignment[], now: string): AssignmentSummary`
- `filterAssignments(assignments: readonly Assignment[], filter: AssignmentFilter, now: string): Assignment[]`
- `buildDashboardData(assignments: readonly Assignment[], filter: AssignmentFilter, now: string): DashboardData`

`buildDashboardData` возвращает сводку исходного списка и новый отсортированный массив видимых заданий. Входной массив и объекты заданий не мутируются.

**Context:**

- Просрочено задание с валидным `dueAt`, у которого метка времени строго меньше `now` и статус `todo` или `in_progress`. Статус `done` просрочку не получает. Невалидный `dueAt` просрочку не получает и исключения не вызывает. Невалидный `now` тоже не вызывает исключения: просроченных тогда нет.
- Сравнение времени идёт по результату `Date.parse`, не по тексту строки и не через `moment`.
- Сводка (`total`, `todo`, `inProgress`, `done`, `overdue`) считается по исходному списку. Просроченный `todo` входит и в `todo`, и в `overdue`. Выполняется `total = todo + inProgress + done`.
- Фильтр — конъюнкция. `status = "all"` пропускает любой статус. Иначе статус совпадает. При `onlyOverdue = false` просроченное задание остаётся, если совпали статус и предмет. Пустой `course` после `trim` означает все предметы. Иначе сравнивай `trim` и `toLocaleLowerCase("ru")`. Пробелы внутри строки значимы.
- `onlyOverdue = true` и `status = "done"` дают пустой видимый список, сводка при этом остаётся сводкой исходного списка.
- Порядок видимого списка: просроченные; затем валидный `dueAt` по возрастанию; при равной метке `title` через `localeCompare` с локалью `ru`; невалидные даты после всех валидных, между собой по `title` локалью `ru`; при полном равенстве ключей сохраняется исходный порядок.
- Приоритет на расчёты не влияет. Тип `any`, утверждения `as any`, `@ts-ignore`, `@ts-expect-error`, default-экспорт и `var` запрещены. Экспортируемые функции объявляй как `export function` с явным возвращаемым типом.
- Типы возьми из спецификации: `Assignment`, `AssignmentFilter`, `AssignmentSummary`, `DashboardData`, а также `AssignmentStatus` и `AssignmentPriority`.

**Format:** Короткий план на 2–4 пункта, затем целый файл модуля без заглушек. Функции чистые, импортов React и доступа к часам внутри них нет. Кратко перечисли, как закрыты пять краевых случаев спецификации: пустой список, все готово и дата в прошлом, битая дата, пробелы в предмете, `onlyOverdue` вместе со статусом `done`.

### Промпт шага 3

**Role:** Ты разработчик, который проверяет чистые доменные функции приложения «Дедлайн» автоматическими тестами. Интерфейс и браузер не затрагиваешь.

**Task:** Напиши модульные тесты на функции шага 2: `isAssignmentOverdue`, `summarizeAssignments`, `filterAssignments`, `buildDashboardData`. Тесты фиксируют спецификацию шага 1 и не подгоняют ожидание под случайную реализацию.

**Context:**

- Вход каждого теста задаёт список, фильтр и `now` явно. Тест не читает системные часы.
- Просрочка: валидный `dueAt` строго раньше `now` и статус `todo` или `in_progress`. Равенство меток просрочкой не является. `done` с прошлой датой в `overdue` не входит.
- Сводка всегда по исходному списку. Отфильтрованный список на `total`, `todo`, `inProgress`, `done`, `overdue` не влияет. Один просроченный `todo` увеличивает оба счётчика, `todo` и `overdue`.
- При `onlyOverdue = false` фильтр статуса оставляет просроченные задания этого статуса.
- Предмет: ` "  Алгебра " ` совпадает с фильтром `"алгебра"`. Фильтр `"   "` означает все предметы. Различие во внутренних пробелах оставляет задание за бортом.
- Сортировка: просроченные раньше остальных; внутри группы валидные даты по возрастанию; равные метки — по `title` локалью `ru`; невалидный `dueAt` в конце; одинаковые ключи сохраняют исходный порядок.
- Битый `dueAt` и битый `now` не приводят к исключению. При битом `now` просроченных нет.
- Запрещены `any`, `@ts-ignore`, `@ts-expect-error` и `moment`.

Обязательные случаи:

1. Пустой список: пустые `items` и нулевая сводка.
2. Все задания `done` с датой в прошлом: `overdue = 0`; при `onlyOverdue = false` список полон и отсортирован по дате; при `onlyOverdue = true` видимый список пуст, а `done` в сводке равен размеру исходного списка.
3. Битая дата среди валидных: функция завершается, задание не просрочено, в отсортированном списке стоит после валидных дат.
4. Пробелы и регистр предмета, включая фильтр из одних пробелов.
5. `onlyOverdue = true` и `status = "done"` при смешанном исходном списке: `items` пуст, сводка всё ещё показывает `done` и `overdue` исходного списка.
6. Дополнительно: просроченный `todo` виден при статусе `todo` и `onlyOverdue = false`; две одинаковые валидные даты упорядочены по русскому `title`; входной массив после вызова остаётся прежним.

**Format:** Короткий план, затем целый файл тестов. На каждый случай — отдельный тест с говорящим именем. В утверждениях проверяй и состав `items`, и все пять полей сводки, и порядок `id` или `title`. Без запуска браузера и без рендера компонентов.
